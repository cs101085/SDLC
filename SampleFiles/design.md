# Problem Definition
Today, in the Rules Editor (BETA) canvas (`RulesEditor_v2/src/RuleEditor.js` and `src/nodes/`), Action Taker and Info Collector nodes (rendered by the shared `RuleNode.jsx`, used by `ActionTakerNode.jsx` and `InfoCollectorNode.jsx`) expose no right-click menu and no keyboard shortcuts. Every everyday change to one of these components — enable/disable, reorder, move an Action Taker to another Decision Maker, delete — requires either opening the component's edit dialog (double-click) or dragging/redrawing canvas connections. A bare `Delete`/`Backspace` key press with such a component selected deletes it immediately, with no confirmation, unlike a Decision Maker, which already asks for confirmation (see Root Cause). The requirements (Sections 2–6) specify a right-click context menu, mirrored keyboard shortcuts, and a delete confirmation for both component types.

Current Behavior:
- Right-clicking an Action Taker or Info Collector does nothing; `RuleNode.jsx` has no `onContextMenu` handler and `RuleEditor.js`'s `<ReactFlow>` element has no `onNodeContextMenu` prop.
- No per-action keyboard shortcuts exist for these components; the only keyboard handling present for any component type is `DecisionMakerNode.jsx`'s `handleKeyPress`, which is scoped to Decision Makers only and out of this ticket's scope.
- Pressing `Delete`/`Backspace` with an Action Taker or Info Collector selected deletes it immediately: ReactFlow's built-in `deleteKeyCode` (`RuleEditor.js`, `deleteKeyCodes` memo, line ~112) removes the node via `onNodesChange`, and `onNodesDelete` (line ~1205) then reconnects the surrounding edges and resizes/repositions Action Taker siblings — all with no confirmation step.
- Enabling/disabling, reordering within a sequence, and moving an Action Taker to a different Decision Maker are possible today only via the edit dialog (`NodeForm.js`'s `Enabled` checkbox, wired through `data.saveNodeData`) or by manually deleting and redrawing connections / dragging the Action Taker across the canvas (the reparenting logic already implemented in `onNodeDragStop`, `RuleEditor.js` lines ~1102–1196).
- `DialogBox.jsx` (`ConfirmationBox`) already renders a `Confirm`-titled dialog with `Cancel` (first) and `OK` buttons, used today for "new rule" and "open rule" confirmations (`RuleEditor.js` lines 152, 831), but is not wired to Action Taker/Info Collector deletion, and neither button currently sets `autoFocus`.
- `DecisionMakerNode.jsx`'s own `handleKeyPress` (lines 95–107) already demonstrates the pattern of intercepting `Delete`/`Backspace` at the node level and calling `e.stopPropagation()` to block ReactFlow's built-in deletion when the user does not confirm — but it uses a synchronous `window.confirm` call, explicitly marked in a code comment as a stand-in ("demo") pending replacement, and only applies to Decision Makers, which are out of this ticket's scope.
- `Marshaller.js` (lines ~422–500) and `onNodesDelete`/`onNodeDragStop` in `RuleEditor.js` confirm the requirements' assumption that component order and parentage are derived purely from canvas connections (edges and `parentNode`), not canvas position — `repositionNodes`/`autoArrange` (`ReactFlowUtils.js`, wired into `Sidebar.js` as "Auto Arrange") already exists as the mechanism referenced by REQ-2.6/REQ-3.6 for repositioning nodes to match a new connection order.

Expected Behavior (per requirements.md Sections 2–6):
- Right-clicking an Action Taker or Info Collector opens a fixed-order context menu with Enable/Disable, Move Forward, Move Backward, (Action Taker only) Send to Next/Previous Decision Maker, Edit, and Delete, each showing its two-key shortcut and Material icon.
- The same single selected component's context menu can be opened by keyboard (Menu key or Shift+F10); items are reachable and operable via Arrow Up/Down (wrapping, including disabled items), Enter, and Escape, per Section 4.
- Every shortcut acts on the single selected component whether or not its menu is open, is suspended while the edit dialog or any text field has focus, and never duplicates a browser-reserved combination.
- Delete, from the menu, its shortcut, or a bare `Delete`/`Backspace` key press, always opens a `Confirm` dialog (`Cancel` focused by default) before removing the component; deletion only proceeds on `OK`.

Root Cause: Not applicable — this is a Feature request, not a bug. The nearest related defect-like gap is in `DecisionMakerNode.jsx`'s `handleKeyPress`, where a `window.confirm` placeholder (explicitly marked "demo" in a code comment) stands in for a proper confirmation dialog for Decision Maker deletion; that gap is for Decision Makers, which the requirements explicitly place out of scope, so it is not corrected here, but its existence confirms the deletion-without-confirmation problem the ticket describes for Action Takers and Info Collectors.

Assumptions and Unknowns:
- Per requirements.md A-1–A-13, the detailed behaviour (icon choices, exact shortcuts, greyed-out-but-focusable items, deletion wording, etc.) is settled; this design follows them without reopening them.
- ReactFlow 11.7.4's node selection model allows more than one node to be multi-selected (default `multiSelectionKeyCode`); the requirements state the editor "selects one component at a time today" (ticket Scope). This design treats "exactly one component selected" as the gating condition for opening the keyboard menu and for the per-action shortcuts, per REQ-4.2/REQ-4.9, regardless of how single/multi-selection is otherwise enforced elsewhere in the editor; multi-select behavior itself is unchanged and out of scope.
- The two edit dialogs (`NodeForm.js` for Action Taker/Info Collector, `DecisionNodeForm.js` for Decision Maker) are unchanged, per requirements.md REQ-2.2/REQ-3.2.
- "Focus is in the edit dialog or a text field" (REQ-4.10, REQ-6.2) is detected by inspecting `document.activeElement` (its tag, or whether it sits inside the open MUI `Dialog`'s DOM subtree) rather than by lifting new "is modal open" state, since MUI's `Dialog` already traps focus inside itself while open; this is an implementation-level choice, noted here because it affects where the shortcut-suspension check is evaluated.

# Proposed Solution
Add the context menu, shortcuts, and delete confirmation to the single shared `RuleNode.jsx` component that already renders both Action Taker and Info Collector nodes, and extend `RuleEditor.js` — the component that already owns the canvas's nodes/edges state and the structural operations ( `onNodesDelete`, `onNodeDragStop`, `saveNodeData`) — with the handful of new graph operations (move forward/backward, send to next/previous Decision Maker) and the document-level keyboard listener needed for shortcuts that must work regardless of focus location on the canvas. Reuse existing extension points wherever the codebase already has one, rather than building parallel mechanisms:

- **Menu widget**: `@mui/material`'s `Menu`/`MenuItem` (already a project dependency, used elsewhere for dropdowns such as `ParameterEnumItem.jsx`) anchored with `anchorReference="anchorPosition"` for right-click and anchored to the node's DOM element for keyboard-triggered opens. MUI's `Menu`/`MenuList` natively implements wrapping Arrow Up/Down navigation, Enter-activates-focused-item, Escape-closes, and (via `disabledItemsFocusable`) keeps disabled items reachable by arrow keys while skipping them on Enter — this satisfies REQ-4.3–REQ-4.6 and A-9/A-10 with configuration, not new code. `autoFocusItem` is set to `true` only when the menu is opened via keyboard, satisfying A-9's distinction between keyboard-opened (first item focused) and mouse-opened (nothing focused until an arrow key) menus.
- **Icons**: `@mui/icons-material`'s `ToggleOn`, `ToggleOff`, `ArrowDownward`, `ArrowUpward`, `ArrowForward`, `ArrowBack`, `Edit`, and `DeleteForever` — all from the package already installed; `DeleteForever` is already used for deletion elsewhere in the editor (`RulesForm.js`, `Condition.jsx`, `ConditionAccordion.jsx`), confirming A-8's "matching the icon the Rules Editor already uses elsewhere for deletion."
- **Delete confirmation dialog**: reuse `DialogBox.jsx` (`ConfirmationBox`) and the `confirmMsg`/`setConfirmBox`/`closeConfirmBox` state already defined in `RuleEditor.js` and already prop-drilled once (to `Sidebar.js` for "new rule"/"open rule" confirmations). No new confirmation UI component is introduced. `ConfirmationBox` already renders the title `Confirm` with `Cancel` first and `OK` second, matching REQ-6.4 exactly.
- **Order/parentage mutation**: model Move Forward/Backward as an edge swap between the selected component and its neighbour (the same edge-chain pattern `Marshaller.js` reads when it derives `Sequence`, and the same reconnect-the-neighbours pattern `onNodesDelete` already performs when removing a node). Model Send to Next/Previous Decision Maker on the existing Action-Taker-reparenting logic in `onNodeDragStop` (same `parentNode`/`extent`/position-offset update, and the same "connect after the last existing Action Taker, or become the first" edge wiring), but update the existing node in place (no drag coordinates to reconcile) instead of building a drag-stop replica node.
- **Deletion execution**: perform it through the same mechanism as today's Delete-key path — `reactFlowInstance`/`useReactFlow().deleteElements({ nodes: [{ id }] })` — so the already-working edge-reconnection and Action-Taker resize/reposition logic in `onNodesDelete` (lines 1205–1253) continues to run unchanged; the new code only decides *when* that path runs (after `OK`), not *what* it does.
- **Repositioning after Move/Send**: none is added; per REQ-2.6/REQ-3.6, the existing "Auto Arrange" action (`autoArrange` in `RuleEditor.js`, exposed via `Sidebar.js`) is the action the user is told to use, unchanged.

Solution Form: Code change (new React components/handlers) built entirely on extension points the React Rules Editor (BETA) already provides (MUI `Menu`, the existing `ConfirmationBox`, the existing node-level keyboard-interception pattern from `DecisionMakerNode.jsx`, and the existing edge-reconnection/reparenting logic in `RuleEditor.js`). No new library, no server-side change: `rulesTranslator.jsp` is untouched because every new action is an in-memory canvas edit, exactly like existing drag-and-drop reordering, and becomes durable only through the existing `SaveRule` flow (REQ-5.6).

Backwards Compatibility:
- Right-click menu and keyboard shortcuts: purely additive. A right-click on an Action Taker or Info Collector currently does nothing useful (ticket Problem statement), so no existing user behavior is removed; double-click-to-edit is unchanged.
- Deletion confirmation: this is a behavior change for every existing user — a bare `Delete`/`Backspace` on a selected Action Taker or Info Collector no longer deletes immediately. No switch gates this change. Per the design-principles exception for "a correction of plainly broken behavior... lost or corrupted data," immediate, unconfirmed deletion of a rule component is exactly the data-loss-prone gap the ticket's Problem statement and Markers of Success identify ("No Action Taker or Info Collector is deleted without the user confirming"); Decision Makers already require confirmation today, so this change brings Action Takers and Info Collectors into line with the editor's own existing precedent rather than introducing an inconsistent new behavior. No user can reasonably depend on an accidental, unconfirmed deletion remaining accidental and unconfirmed.
- `DialogBox.jsx` gains an `autoFocus` prop on its `Cancel` button so default focus lands there (REQ-6.4, REQ-6.10). This affects the two other call sites ("new rule", "open rule" confirmations) as well, but only by giving them the same safe default-focus behavior; no existing call site relies on `OK` having default focus.

UI Consistency: Rules Editor (BETA) canvas (`RulesEditor_v2`), following the Decision Maker node's existing keyboard-interception pattern (`DecisionMakerNode.jsx`) and the editor's existing confirmation dialog (`DialogBox.jsx`/`ConfirmationBox`).
- Entry points: right-click on an Action Taker or Info Collector node (new `onContextMenu`/`onNodeContextMenu` handling); the Menu key or Shift+F10 when exactly one such node is selected and focus is on the canvas.
- Hierarchy: a single-level MUI `Menu` with the seven (Action Taker) or five (Info Collector) items in the fixed order from requirements.md Section 2/3, each showing its icon, label, and shortcut text; no submenu or progressive disclosure needed at this scale.
- States: normal (all items enabled, click/Enter active); unavailable (Move Forward/Backward at a sequence boundary, Send to Next/Previous Decision Maker with no such neighbour) rendered as a greyed-out, non-activating but still keyboard-focusable `MenuItem` (`disabled` with `disabledItemsFocusable` on the parent `Menu`); no loading, empty, or error state applies (Section 5.2–5.3). Enable/Disable, Move, and Send actions show no success/failure notification (A-13); Delete's only feedback is the component's removal from the canvas, matching existing deletion behavior elsewhere in the editor.
- Validation/confirmation: no validation on any menu item; Delete alone requires confirmation via the reused `Confirm` dialog, with `Cancel` defaulted and focused, `OK` destructive, worded per-component-type per A-12.
- Permissions: identical to who can already open the Rules Editor (BETA) and edit a rule today; no new role.
- Accessibility: every shortcut is exposed via `aria-keyshortcuts` (or MUI's equivalent prop) alongside the visible label so it is announced to assistive technology (REQ-4.7); keyboard-opened menus move focus to the first item immediately, mouse-opened menus do not pre-focus (A-9); Escape returns focus to the triggering node; disabled items remain reachable by Arrow Up/Down but inert on Enter (A-10).

Other Systems: none — `rulesTranslator.jsp`, the Rules Engine runtime, and the GWT editor are untouched; every new action is an in-memory canvas edit that only becomes durable through the existing, unmodified `SaveRule` call.

Workaround:
- None identified. The underlying actions (enable/disable via the edit dialog, reorder via deleting and redrawing connections, moving an Action Taker via drag-and-drop, deleting with the existing lack of confirmation) are already available today exactly as the ticket's Problem statement describes; there is no interim configuration or data change that adds a menu, shortcuts, or a confirmation step without this code change.

Alternatives Considered:
- A context menu rendered from inside each node component (`ActionTakerNode.jsx`/`InfoCollectorNode.jsx` individually) instead of the shared `RuleNode.jsx`: rejected because both node types already delegate their entire rendering to `RuleNode.jsx`, which is exactly where `DecisionMakerNode.jsx`'s analogous (if simpler) keyboard-interception code already lives for its own node type; building the menu once in `RuleNode.jsx` avoids duplicating it between `ActionTakerNode.jsx` and `InfoCollectorNode.jsx`.
- Keeping ReactFlow's built-in `deleteKeyCode` prop and trying to intercept deletion only in the already-existing `onNodesDelete` callback: rejected because `onNodesDelete` fires only after ReactFlow has already applied the node-removal change; by then the node is already gone from `nodes`/`edges` state and the deletion cannot be cancelled without re-inserting the node (which would also discard any further state ReactFlow internally recomputed). Intercepting at the node's own `onKeyDown` with `e.stopPropagation()` — the same technique `DecisionMakerNode.jsx` already applies, just swapping the synchronous `window.confirm` for the existing async `ConfirmationBox` — stops the deletion before it happens.
- Building a brand-new "replica node" for Send to Next/Previous Decision Maker, mirroring `onNodeDragStop`'s approach exactly: rejected in favor of updating the existing node's `parentNode`/`extent`/position fields in place, because the drag-stop code's replica-node approach exists to cleanly reset drag-related transient state (`isNodeDragged`, drag deltas) that a menu-triggered, non-drag action never acquires; mutating the existing node in place is simpler and matches the in-place mutation style `saveNodeData` already uses for the same nodes.

- Modify: `RulesEditor_v2/src/utils/ReactFlowUtils.js` — add helper(s) to compute each menu item's availability for a given node (is it last/first in its sequence; does its Decision Maker have a next/previous Decision Maker), alongside the existing `hasCycles`/`getEdgeParams` graph helpers, so `RuleNode.jsx`/`ComponentContextMenu.jsx` can grey out items per A-1/A-7 without duplicating graph-walking logic already used elsewhere (`Marshaller.js`, `onNodesDelete`).
- No change: `RulesEditor_v2/src/utils/Marshaller.js`, `src/utils/Api.js`, `webapps/admin/rulesTranslator.jsp`, any Rules Engine Java component or database script — the saved rule's XML shape, its `Sequence` derivation, and every server-side contract are unaffected, because every new action only changes in-memory canvas nodes/edges that already feed the existing, unmodified save path.

# Data and Control Flow
Before:
- User double-clicks an Action Taker/Info Collector → `RuleNode.jsx`'s `handleOpen` → `ModalDialog`/`NodeForm.js` → on save, `data.saveNodeData(...)` updates the node in `RuleEditor.js`'s `nodes` state.
- User selects a component and presses `Delete`/`Backspace` → ReactFlow's `deleteKeyCode` removes the node from `nodes` via `onNodesChange` → `onNodesDelete` (`RuleEditor.js`) reconnects the edges around the gap and resizes/repositions Action Taker siblings. No confirmation step exists.
- User reorders/moves components by manually deleting and redrawing connections, or by dragging an Action Taker onto another Decision Maker (`onNodeDragStop`, `RuleEditor.js`), which removes the dragged node, reconnects its old neighbours, and inserts a new replica node parented to the target Decision Maker with a recalculated position.
- A later Save posts the current `nodes`/`edges` to `rulesTranslator.jsp`'s `SaveRule`, via `Marshaller.js`'s XML builder, which derives each component's `Sequence` purely by walking the canvas's edges/`parentNode` relationships.

After:
- Right-click on an Action Taker/Info Collector, or Menu key/Shift+F10 with exactly one such node selected and canvas focus → `RuleNode.jsx` opens `ComponentContextMenu.jsx`, anchored at the click point or at the node, with item availability computed from the current `nodes`/`edges` via the new `ReactFlowUtils.js` helper(s).
- Choosing (or using the shortcut for) Enable/Disable, Edit, Move Forward/Backward, or Send to Next/Previous Decision Maker calls the corresponding callback prop-drilled from `RuleEditor.js` (or, for Enable/Disable and Edit, the node's own existing `saveNodeData`/`handleOpen`), which updates `nodes`/`edges` in place; the menu, if open, closes.
- Choosing (or using the shortcut for) Delete, or pressing a bare `Delete`/`Backspace` on the selected node, always calls `e.stopPropagation()` at the node (so ReactFlow's built-in `deleteKeyCode` never fires) and opens the existing `ConfirmationBox` via `setConfirmBox` with the per-type message from A-12; choosing `OK` calls `reactFlowInstance.deleteElements({ nodes: [{ id }] })`, which re-enters the existing, unmodified `onNodesDelete` edge-reconnection/resize path; choosing `Cancel` or Escape leaves the canvas untouched and the component selected.
- Save continues to call the unmodified `Marshaller.js`/`rulesTranslator.jsp` `SaveRule` path; because every new action only ever rewires edges/`parentNode` the same way existing drag-and-drop and deletion logic already does, the derived `Sequence` values and saved XML shape are unaffected.

Rollback and Compatibility:
- The change is isolated to `RulesEditor_v2` source and its rebuilt zip; reverting the commit (including the zip) fully restores prior behavior, with no database or server-side change to undo.
- A rule saved after using the new menu/shortcuts produces the same `Sequence`-ordered XML a rule arranged by hand would, so no migration or re-save of existing rules is needed.

# Risks and Mitigations
- Risk: Intercepting `Delete`/`Backspace` only at the node's `onKeyDown` may not reliably stop ReactFlow's internal `deleteKeyCode` listener if ReactFlow attaches its listener at a DOM level the event does not bubble through in all browsers.
  Mitigation: Verify against the already-shipped precedent in `DecisionMakerNode.jsx`, which uses exactly this `e.stopPropagation()` technique for Decision Makers today; if coverage gaps appear, remove `'Backspace'`/`'Delete'` from `deleteKeyCodes` entirely and reimplement confirmed-deletion as the sole path for every node type consistently.
- Risk: A document-level keydown listener for the global per-action shortcuts could fire while focus is inside the edit dialog or a text field elsewhere in the app (e.g., the sidebar's filter fields), violating REQ-4.10.
  Mitigation: Gate the listener on `document.activeElement` not being (or not being inside) an `input`/`textarea`/`select`/content-editable element or the open MUI `Dialog`'s DOM subtree, mirroring how MUI's own focus trap already isolates the open dialog.
- Risk: MUI `Menu`'s default keyboard navigation may not, out of the box, keep disabled items focusable (A-10) without `disabledItemsFocusable` explicitly set, or may not restore focus correctly to an `anchorPosition`-anchored (coordinate-only) menu's trigger on Escape (REQ-4.6).
  Mitigation: Explicitly set `disabledItemsFocusable` on the `Menu`; for Escape's focus return, keep a ref to the triggering node's DOM element (not just coordinates) and call `.focus()` on it in the menu's `onClose`.
- Risk: The new Move Forward/Backward and Send-to-Decision-Maker edge rewiring could produce an inconsistent graph (e.g., a dangling edge, or a cycle) if an edge case in the existing edge-walking assumptions (one outgoing/incoming Decision-Maker-to-Decision-Maker edge, per A-1) is not actually guaranteed by all existing rules.
  Mitigation: Reuse the exact edge-finding and reconnect patterns already proven in `onNodesDelete`/`onNodeDragStop`/`Marshaller.js` rather than writing new graph-walking logic, and grey out the corresponding menu item whenever that assumption does not hold (A-1/A-7), exactly as `isValidTarget`-style checks already do elsewhere in the node components.
- Risk: Changing `DialogBox.jsx`'s default button focus affects the two unrelated existing confirmations ("new rule", "open rule").
  Mitigation: `Cancel`-as-safe-default is consistent with both existing uses (both are "are you sure you want to discard/replace current changes" prompts where `Cancel` is the safer choice); no existing behavior is relied upon.

- Regression: after Move Forward/Backward, Send to Next/Previous Decision Maker, and Delete, save the rule through the existing `SaveRule` flow and confirm (e.g., via `GetRuleXML`/`exportRule.sh`, or by reopening the rule) that the resulting `Sequence` values and connections match the worked examples in requirements.md REQ-2.6/REQ-2.8/REQ-6.6; confirm the unaffected GWT editor (`RulesEditor/`) still opens and runs the same rule unchanged, since no database or XML-shape change was made.
- UI/accessibility: verify each menu item's shortcut is exposed to assistive technology (e.g., via `aria-keyshortcuts`) alongside its visible label; verify contrast and keyboard-only operability of the menu and the confirmation dialog consistent with the rest of the editor.
